### **2. Enhance Section 2: Architecture Overview**

**Add a clarification paragraph after the workspace table:**

#### **2.1 Access Control and Tenancy Model**

The platform implements a **unified tenancy model** across all workspaces with role-based access segregation rather than model-type or purpose-based isolation. This design decision provides several benefits:

- **Collaboration Enablement**: Data Scientists, ML Engineers, and Analysts can collaborate on shared models and datasets without artificial boundaries
- **Resource Optimization**: Shared compute and storage resources with governance through workspace-level policies and quotas
- **Simplified Management**: Centralized access control through Unity Catalog eliminates complexity of managing multiple isolated tenancies
- **Flexibility**: Models of different types (predictive, classification, recommendation, etc.) and purposes (customer analytics, risk modeling, operational optimization) coexist within the same workspace with appropriate RBAC controls

Access segregation is enforced through Unity Catalog permissions mapped to AD groups based on user roles, not model characteristics.

#### **5.2 Cluster Security Mode (CSM) and Authentication Strategy**

**Workspace Security Posture:**

The platform implements differentiated security configurations aligned with each workspace's operational requirements:

| Workspace | Security Approach | Interactive Access | Deployment Method |
|-----------|-------------------|-------------------|-------------------|
| **Prod Analytics** | Development-optimized security enabling interactive notebooks, ad-hoc queries, and collaborative experimentation | Full interactive access for Data Scientists and ML Engineers | Code commits to GitLab Dev/Feature Branch |
| **Prod Parallel** | Pre-production security posture balancing validation needs with production-like controls | Limited privileged access for configuration and validation (throttling, canary, blue-green testing) | Automated deployment via UAT Runner |
| **Prod** | Strictest production security - zero interactive access, all operations audit-logged | No human interactive access - service principals only | RTB Change Request approved automated deployment via Prod Runner |

**CI/CD Authentication Architecture:**

- **Centralized Secret Management**: All CI/CD pipeline authentication credentials are stored in Barclays central secrets vault (not GitLab environment variables or repository configs)
- **Service Principal Strategy**: Each workspace utilizes appropriate service principals with least-privilege access for GitLab runner operations
- **Credential Rotation**: Automated credential rotation policies ensure secrets are regularly updated without manual intervention
- **Audit Trail**: All service principal activities are logged to Unity Catalog audit logs for compliance and security monitoring

**Guild Alignment:**

The CSM implementation strategy has been reviewed and approved by the guild, ensuring:
- Compliance with Barclays enterprise security standards
- Alignment with data classification and handling requirements
- Adherence to segregation of duties principles
- Regular security configuration reviews as part of governance processes

### **7. Add New Section: FAQ / Common Questions**

#### **Frequently Asked Questions**

**Q1: Why don't we have separate workspaces for different model types?**

A: We implement role-based access control through Unity Catalog rather than workspace-level segregation. This approach enables better collaboration, resource optimization, and simpler governance while maintaining appropriate security controls.

**Q2: How is data in the temporary S3 bucket protected?**

A: The bucket has IAM policies restricting access exclusively to the Databricks workspace, resides within the Barclays VPC, and implements automatic retention policies. No downstream systems can access this bucket.

**Q3: What happens if someone tries to deploy directly to production?**

A: Direct deployment to production is prevented through multiple controls: (1) No interactive access to Prod workspace, (2) GitLab Prod Runner only triggers on approved Change Requests, (3) RTB team acts as gatekeeper for all production deployments.

**Q4: How are credentials managed for CI/CD pipelines?**

A: All credentials are stored in Barclays central secrets vault and accessed programmatically. No passwords or tokens are stored in GitLab environment variables or repository configurations, maintaining security while enabling automation.

**Q5: Can models be moved between workspaces without retraining?**

A: Model binaries are published to Nexus (Model Registry) from Prod Parallel workspace after successful testing. The Prod Runner deploys these pre-validated binaries to Prod workspace, ensuring consistency without retraining.
